Visão geral

Consultoria técnica em migração de dados entre plataformas jurídicas concorrentes e o Legal One — da extração direta em banco até a carga final, com pipeline documentado e versionado em repositório Git compartilhado com o time.

Problema resolvido

Trocar de sistema de gestão exige levar todo o histórico — contatos, processos, serviços, andamentos, posições financeiras — sem perder dados nem quebrar relações entre entidades. Acima de poucas centenas de registros, isso só funciona com um processo padronizado; sem ele, cada migração reinventa a lógica do zero.

Contexto

As migrações partiam de diferentes plataformas concorrentes (identificadas internamente como Astrea, Projuris, CPJ e CP-PRO, entre outras) com modelos de dados distintos entre si e diferentes do Legal One. O trabalho era executado via scripts SQL diretamente contra o banco de origem (abordagem "banco a banco"), complementado por um modelo de planilha padronizado (X-One) para os casos em que a extração direta não era possível.

Minha atuação

  • Desenvolvimento e manutenção de scripts SQL de extração, organizados por módulo de dados (Contatos, Processos, Serviços).
  • Construção de rotinas de pré-tratamento no banco de origem e de pré-tratamento no banco de destino antes da carga (CPF duplicado, endereço, e-mail duplicado, cadastro de posições).
  • Execução de verificações de integridade e correções pós-carga.
  • Colaboração contínua em repositório Git compartilhado pelo time de migração, versionando scripts SQL e planilhas de tratamento "De/Para" por cliente.
  • Aplicação prática desse processo em projetos reais a partir de múltiplas plataformas concorrentes.

Tecnologias utilizadas

SQL Server (T-SQL) Git / GitHub Excel (planilhas De/Para) PowerShell

Solução implementada

O processo é estruturado como um pipeline de 4 fases, versionado em repositório Git compartilhado com o restante do time:

  • Pré-extração (banco de origem) — funções e tabelas temporárias auxiliares: máscara de número de processo (padrão CNJ), flags de cliente/parte, temporárias para etiquetas e envolvidos em audiências/eventos/prazos/tarefas.
  • Extração por módulo — consultas organizadas em três módulos centrais: Contatos (dados cadastrais, endereços, telefones, grupos, subcontatos, usuários, andamentos, compromissos/tarefas), Processos (dados principais, apensos, classificações financeiras, contas judiciais, etiquetas, garantias, objetos, pedidos, posições, timesheet) e Serviços (dados principais, andamentos, classificações financeiras, compromissos/tarefas, vínculos).
  • Pré-migração (banco de destino) — CPF duplicado, endereço, correção de posições de terceiros, cadastro de posições, e-mail duplicado.
  • Pós-migração — checagem de integridade, inserção de etiquetas, vínculo de comentários de andamento às tarefas, correção de horário perdido na carga.

Processo técnico

Banco de origem (concorrente)
  └─> Pré-extração: funções auxiliares + tabelas temporárias
       └─> Extração por módulo (Contatos / Processos / Serviços) via SQL
            └─> Planilha "De/Para" (tratamento específico por cliente)
                 └─> Pré-migração no destino: CPF, endereço, e-mail, posições
                      └─> Carga no Legal One
                           └─> Pós-migração: integridade, etiquetas, vínculos, correções

Desafios e decisões

  • Modelos de dados incompatíveis: cada plataforma de origem organiza contatos, processos e serviços de forma diferente — mapeamento manual de campo a campo e de relacionamento a relacionamento.
  • Integridade referencial: campos derivados (ex.: se um contato é cliente ou parte) precisaram ser calculados via consultas específicas antes da extração.
  • Volume de dados: em pelo menos um projeto, o script de carga ultrapassou 170 MB e precisou ser fracionado via PowerShell.
  • Padronização vs. caso a caso: o pipeline é genérico e reutilizável, mas cada cliente exige ajustes pontuais, registrados sem comprometer o processo padrão.

Overview

Technical consulting on data migration between competing legal platforms and Legal One — from direct database extraction to final load, with a documented pipeline version-controlled in a Git repository shared with the team.

Problem solved

Switching systems means bringing the entire history — contacts, cases, services, activity logs, financial positions — without losing data or breaking relationships between entities. Beyond a few hundred records, this only works with a standardized process; without one, every migration reinvents the logic from scratch.

Context

Migrations originated from several different competing platforms (internally identified as Astrea, Projuris, CPJ, and CP-PRO, among others), each with its own data model, all different from Legal One's. Work was executed via SQL scripts run directly against the source database, complemented by a standardized spreadsheet template (X-One) when direct extraction wasn't possible.

My role

  • Development and maintenance of SQL extraction scripts, organized by data module (Contacts, Cases, Services).
  • Building pre-processing routines on the source database and pre-load processing on the target database (duplicate tax-ID, address, duplicate email, position registration).
  • Running post-load integrity checks and corrections.
  • Ongoing collaboration in a shared Git repository, versioning SQL scripts and client-specific mapping spreadsheets.
  • Practical application of this process across real migration projects from multiple competing platforms.

Technologies used

SQL Server (T-SQL) Git / GitHub Excel (mapping spreadsheets) PowerShell

Solution implemented

The process is structured as a 4-phase pipeline, version-controlled in a shared Git repository:

  • Pre-extraction (source database) — helper functions and temporary tables: case-number masking (CNJ standard), client/party flags, temporaries for tags and people involved in hearings/events/deadlines/tasks.
  • Extraction by module — queries organized into three core modules: Contacts, Cases, and Services.
  • Pre-migration (target database) — duplicate tax-ID, address, third-party position correction, position registration, duplicate email.
  • Post-migration — integrity checks, tag insertion, linking activity-log comments to tasks, fixing time inconsistencies.

Technical process

Source database (competitor platform)
  └─> Pre-extraction: helper functions + temporary tables
       └─> Extraction by module (Contacts / Cases / Services) via SQL
            └─> "Mapping" spreadsheet (client-specific treatment)
                 └─> Pre-migration on target: tax ID, address, email, positions
                      └─> Load into Legal One
                           └─> Post-migration: integrity, tags, links, corrections

Challenges and decisions

  • Incompatible data models: every field and relationship had to be manually mapped for equivalence.
  • Referential integrity: derived fields had to be computed via dedicated queries before extraction.
  • Data volume: on one project, the load script exceeded 170 MB and had to be split via PowerShell.
  • Standardization vs. case-by-case needs: the pipeline stays generic while allowing documented exceptions.
