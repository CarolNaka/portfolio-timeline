      Visão geral

      Migração de dados entre plataformas jurídicas concorrentes (Astrea, Projuris, CPJ e CP-PRO) e o Legal One, da extração direta no banco até a carga final. Cada origem organiza contatos, processos e serviços de um jeito, então o trabalho segue um pipeline padronizado, versionado em repositório Git compartilhado com o time. Quando a extração direta não é possível, uso o modelo de planilha padrão (X-One).

      Minha atuação

      • Scripts SQL de extração organizados por módulo: Contatos, Processos e Serviços.
      • Rotinas de pré-tratamento no banco de origem e no destino (CPF e e-mail duplicados, endereço, posições).
      • Verificações de integridade e correções pós-carga.
      • Versionamento de scripts e de planilhas “De/Para” por cliente, em colaboração contínua com o time.

      Como funciona

      O pipeline tem quatro fases: pré-extração (funções e tabelas temporárias no banco de origem), extração por módulo, pré-migração no destino e pós-migração (integridade, etiquetas, vínculos e correções).

      Banco de origem (concorrente)
  └─> Pré-extração: funções auxiliares + tabelas temporárias
       └─> Extração por módulo (Contatos / Processos / Serviços) via SQL
            └─> Planilha "De/Para" (tratamento específico por cliente)
                 └─> Pré-migração no destino: CPF, endereço, e-mail, posições
                      └─> Carga no Legal One
                           └─> Pós-migração: integridade, etiquetas, vínculos, correções

      Desafios e aprendizados

      • Modelos de dados incompatíveis: mapeamento campo a campo e relação a relação entre cada origem e o Legal One.
      • Integridade referencial: campos derivados (ex.: se o contato é cliente ou parte) calculados por consultas antes da extração.
      • Volume: um script de carga passou de 170 MB e foi fracionado via PowerShell.
      • Padrão x caso a caso: o pipeline é reutilizável, com ajustes pontuais por cliente. Próximos passos: parametrizar esses tratamentos, documentar o pipeline para novos integrantes e registrar o volume migrado por projeto.

      Overview

      Data migration from competing legal platforms (Astrea, Projuris, CPJ, and CP-PRO) into Legal One, from direct database extraction to final load. Each source organizes contacts, cases, and services differently, so the work follows a standardized pipeline, versioned in a Git repository shared with the team. When direct extraction isn't possible, I use the standard spreadsheet template (X-One).

      What I did

      • SQL extraction scripts organized by module: Contacts, Cases, and Services.
      • Pre-treatment routines on both the source and the target database (duplicate tax IDs and emails, addresses, roles).
      • Integrity checks and post-load fixes.
      • Versioning of scripts and per-client “De/Para” mapping spreadsheets, in ongoing collaboration with the team.

      How it works

      The pipeline has four phases: pre-extraction (helper functions and temporary tables on the source database), per-module extraction, pre-migration on the target, and post-migration (integrity, labels, links, and fixes).

      Source database (competitor)
  └─> Pre-extraction: helper functions + temporary tables
       └─> Per-module extraction (Contacts / Cases / Services) via SQL
            └─> "De/Para" spreadsheet (client-specific treatment)
                 └─> Pre-migration on target: tax ID, address, email, roles
                      └─> Load into Legal One
                           └─> Post-migration: integrity, labels, links, fixes

      Challenges and learnings

      • Incompatible data models: field-by-field and relationship-by-relationship mapping between each source and Legal One.
      • Referential integrity: derived fields (e.g., whether a contact is a client or a party) computed by queries before extraction.
      • Volume: one load script exceeded 170 MB and was split using PowerShell.
      • Standard vs. case by case: the pipeline is reusable, with specific adjustments per client. Next steps: parameterize those treatments, document the pipeline for new team members, and record migrated volume per project.
