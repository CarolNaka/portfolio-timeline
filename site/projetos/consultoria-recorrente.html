Consultoria Consulting SQL Server Legal One

Visão geral

Suporte técnico recorrente a clientes já migrados para o Legal One: correções e ajustes diretamente em produção, sempre com plano de reversão (rollback) documentado.

Problema resolvido

Depois da migração, surgem necessidades que a interface do sistema não resolve: dados que vieram errados, regras de negócio específicas, baixa em massa de processos. Isso exige alterar o banco de produção diretamente — uma operação de risco, que precisa de rigor técnico e de um caminho de reversão.

Contexto

Essas demandas chegavam de forma recorrente, uma por cliente, sempre com aprovação formal por e-mail antes da execução. Cada caso tinha sua própria particularidade, mas o processo de execução seguia sempre o mesmo padrão de segurança.

Minha atuação

  • Recebimento e interpretação de solicitações de ajuste vindas de clientes já migrados.
  • Escrita de scripts SQL personalizados (correção de dados, baixa de processos, ajuste de centro de custo, ajuste de tipo de ação, reorganização de objetos).
  • Criação de um script "declarativo" de diagnóstico antes de qualquer alteração.
  • Execução do script de atualização em produção somente após aprovação formal.
  • Criação de um script de rollback para cada ajuste realizado.
  • Comunicação técnica com áreas internas e registro formal de aprovação por e-mail.

Tecnologias utilizadas

SQL Server (T-SQL) E-mail (aprovação) Excel (conferência)

Solução implementada

Cada demanda segue um padrão de 3 arquivos, repetido de forma consistente:

  • Script declarativo — levanta e lista exatamente quais registros serão afetados, sem alterar nada, servindo de base para aprovação.
  • Script de execução — aplica a alteração em produção, já validada e aprovada.
  • Script de rollback — reverte exatamente a alteração feita, preparado antes da execução do ajuste, não depois.

Esse padrão transforma uma operação arriscada em um processo auditável e reversível.

Processo técnico

Solicitação do cliente (e-mail)
  └─> Script declarativo (diagnóstico / escopo do impacto)
       └─> Aprovação formal por e-mail
            └─> Script de execução (update em produção)
                 └─> Script de rollback já preparado (plano de reversão)

Desafios e decisões

  • Risco de alteração em produção: sempre preparar um script de rollback antes de executar mitiga esse risco sistematicamente.
  • Diversidade de demandas: cada cliente trazia uma regra de negócio diferente, exigindo leitura cuidadosa antes de traduzir em SQL.
  • Necessidade de rastreabilidade: aprovação formal por e-mail garante histórico de quem autorizou o quê.

Overview

Ongoing technical support for Legal One clients already migrated: corrections and adjustments directly in production, always with a documented rollback plan.

Problem solved

After migration, needs come up that the system's interface can't resolve: incorrectly loaded data, specific business rules, bulk case closures. These require direct changes to the production database — a risky operation that demands rigor and a rollback path.

Context

These requests arrived on a recurring basis, one per client, always with formal email approval before execution. Each case had its own specifics, but the execution process always followed the same safety standard.

My role

  • Receiving and interpreting adjustment requests from clients already migrated.
  • Writing custom SQL scripts (data correction, case closure, cost-center adjustment, case-type adjustment, object reorganization).
  • Creating a "declarative" diagnostic script before any change.
  • Executing the update script in production only after formal approval.
  • Creating a rollback script for every adjustment made.
  • Technical communication with internal teams and formal email approval records.

Technologies used

SQL Server (T-SQL) Email (approval) Excel (review)

Solution implemented

Each request follows a 3-file pattern, applied consistently:

  • Declarative script — identifies and lists exactly which records will be affected, without changing anything, for review and approval.
  • Execution script — applies the validated, approved change to production.
  • Rollback script — reverts exactly the change made, prepared before executing the adjustment, not after.

This pattern turns a risky operation into an auditable, reversible process.

Technical process

Client request (email)
  └─> Declarative script (diagnosis / scope of impact)
       └─> Formal email approval
            └─> Execution script (production update)
                 └─> Rollback script already prepared (reversal plan)

Challenges and decisions

  • Production change risk: always preparing a rollback script before executing systematically mitigates this risk.
  • Request diversity: each client brought a different business rule, requiring careful reading before translating into SQL.
  • Need for traceability: formal email approval ensures a record of who authorized what.
